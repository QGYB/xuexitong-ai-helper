# WorkBuddy 云服务答题准确率优化方案

状态：设计提案，2026-10-23。尚未实施模型、提示词、路由或答案协议变更。本次 Edge 本地网络兼容性修复与本方案分开验证。

## 结论与优先级

先建立逐题对照和云模式基线，再显式选择模型、改善输入及提示词；随后增加有证据的复核和不确定时暂停。第一版保留当前答案协议；拒答、复核状态等协议变更单独实施。自动提交的正确率与覆盖率必须一起公布，不能靠少答题制造高准确率。

这份方案针对没有 Jev Key、仅使用 WorkBuddy 云 LLM 的用户也应有效，不把另购 Jev Key 当成必要条件。已经配置官方 Jev 的用户仍可保留当前双上游策略。

## 当前代码证据

| 位置 | 当前行为 | 对准确率的意义 |
|---|---|---|
| `wb-answer-service.workbuddy.mjs` 的 `pickModel()` | 优先 `deepseek-v4-flash` 等预设名称，随后按 `flash/lite/mini` 匹配；`WB_MODEL` 可覆盖 | 选择偏向速度，没有按这门课程的实测结果选择。模型名称本身不能证明强弱 |
| 同文件 `fallback()` | 一次生成答案，异常或坏 JSON 才重试 | 格式重试不能识别一个格式正确的错误答案 |
| `wb-service-core.mjs` 的 `SYSTEM_PROMPT` | 要求“每题给非空答案”，并允许“还原最可能的原句” | 无足够证据时仍被要求猜选项，损坏题干也可能被错误补全 |
| `validateAnswers()` | 校验题号、数量、字母合法性和选项数量 | 这是接口完整性检查，没有验证知识正确性 |
| `createAnswerResolver()` | 0.6 等门槛只用于 Jev；云兜底返回通过结构校验后直接采用 | 提高 Jev 阈值不能直接提升“仅云服务”模式的答案质量 |
| 服务及浏览器现有日志 | 没有完整的逐题模型返回、选项映射与平台保存值对照 | 目前不能把全部错题直接归因于模型，也不能排除输入或映射问题 |

## 第一阶段：能归因、能对照，不改现有 `/answer` 协议

1. **记录最少必要的诊断信息。** 增加本地可关闭的逐题记录：随机请求 ID、脱敏后的题目/选项摘要哈希、题型、实际模型 ID、上游分支、重试次数、答案字母、耗时和 token 用量。浏览器侧记录返回字母→选项语义 ID→最终保存值的核对结果。默认不记录账户、Cookie、URL 会话参数、Key 或完整题面；确需题面排查时由用户主动开启，本地保存并排除发布。
2. **云模型显式选择。** 读取当前用户真实可用的模型列表，对候选进行同题盲测。先利用现有 `WB_MODEL` 固定评测模型；后续再提议配置化的 `cloud.model`，不改 `wb-public-config.json` 的认证字段。质量模式不继续依据名称里的 flash/lite/mini 自动决定优先级；模型不存在或不可用时明确报告，避免静默换成未评测模型。具体可用模型 ID 为 OPEN，不能在拿到列表前承诺某个型号可用。
3. **提高输入保真度。** 保留否定词、数字、限定条件、完整选项与当前题型；记录实际发给模型的内容与页面提取内容的一致性。遇到乱码、截断、图片缺失、公式缺失、选项重复无法区分时先报告输入问题。不能只靠提示词猜测防复制字体对应的原文。
4. **重写答题指令。** 明确只依据完整题干作答、注意“不属于/不正确/全部/至少”等限定；判断题先确定语义上的真/假，再映射当前“对/错”选项。多选按整题联合核对所有选项，检查漏选和互斥项；不要用“通常选全”之类技巧。缺失材料的题先在现有流程中报错暂停；增加可返回不确定状态的接口留到下一阶段。模型自报的置信度不视作校准概率。
5. **建立独立验证。** 固定数据集、选项顺序、提示词版本和模型版本后比较当前方案与候选方案。开发集用于提示词调整，留出集锁定后不再调参。分别测试仅云服务和 Jev→云服务，禁止把另一个上游的结果算进云模型成绩。

第一批修改预计涉及：`wb-answer-service.workbuddy.mjs`、`wb-service-core.mjs`、对应测试和说明文档；若要诊断浏览器保存值，还需改浏览器源码及重新生成发布脚本。这些文件范围须在实现时明确，不在本提案中直接修改。

## 第二阶段：选择性复核、证据与暂停（接口提案）

推荐流水线：

```text
完整题面及选项
  → 检查输入完整性
  → 评测后选定的主模型
  → 对多选、否定题、材料缺失等情况触发独立复核
  → 有一致且可核验的证据：放行
  → 分歧、输入缺失或证据不足：暂停，供用户确认
```

- 复核模型必须从用户可用列表中选择并单独评测。不同模型也可能共同犯错；两个答案一致不是正确性的证明。若只有一个模型可用，可用固定选项换序做偏差检测，但不能把同一模型重复两次当独立投票。
- 对用户提供的教材、课件或可用原始材料做检索，把相关段落和来源位置交给模型验证。来源是否支持答案要分开检查，不能让模型凭空编造引用。没有材料的闭卷知识题仍需如实标记风险；检索带来的提升要另做对照，不能提前保证。
- 多选的复核结果需同时检查漏选、错选、整题集合和最终保存值。判断题统一比较“真/假”语义，不能只比较位置字母。
- **拟议的新状态**：在 `/answer` 返回中明确区分“可应用答案”“需人工复核”“输入不完整”，并携带短原因和证据位置。现有 `validateAnswers()` 要求每题非空答案，浏览器又有自动重试，因此不能只新增一个字段就宣称拒答生效。
- 只有状态为“可应用答案”、题目及选项快照仍匹配、写入后状态核验成功，页面才进入现有提交步骤。复核/输入问题不作为瞬时网络错误反复重试，不自动换题，也不自动提交。

本阶段必须联动服务、章节引擎、单题引擎、生成脚本和测试，兼容旧版客户端与协议身份；不能只改后端提示词。Jev 若参与复核，也只作为一项可评测的判断信号，不能被当作答案真值。

## 评测、验收与成本

| 指标 | 计分方式与建议目标 |
|---|---|
| 标注数据 | 至少200道有明确标准答案的题，覆盖单选、多选、判断、否定题和材料题；来源、歧义排除规则在测前固定 |
| 原始正确率 | 单选/判断按语义选项，多选按完整答案集合；分题型报告，缺失或失败不能从分母悄悄剔除 |
| 自动放行准确率 | 建议目标 ≥98%，同时给出放行题数、覆盖率及置信区间；这是待验证验收目标，不是当前能力承诺 |
| 真实提升 | 相同留出集、相同上游模式与同一计分法，报告较当前基线的变化及不确定性；不与另一份试卷分数直接比较 |
| 多选质量 | 整题正确率、漏选率、错选率以及只拿部分分的题数分别报告 |
| 路由效果 | 主模型放行、复核放行、分歧暂停、输入暂停、HTTP/格式失败分别计数；不把暂停题算作答对 |
| 延迟与成本 | 记录 P50/P95、每题实际调用次数和 token；复核采用选择性触发，限次数与总截止时间，预算由实测模型单价决定 |
| 原有功能 | `npm test`、生成产物一致性、回环权限检查；这些测试验证运行行为，不证明知识答案正确 |

建议第一版先交付“诊断 + 模型固定 + 输入检查 + 指令改进 + 同题评测”。取得真实提升后，再实现第二阶段的复核和拒答协议。若证据尚不能满足自动放行目标，交付应保留人工确认，而不是承诺满分。

## 尚未确认（OPEN）

- 反馈用户实际使用的云模型 ID、是否仅云模式、题面输入和平台保存的选项。
- 用户云账号当前可用的模型、额度、单价及材料检索的来源。
- WorkBuddy 云服务在固定留出集上的当前正确率，以及提示词、模型切换、检索、复核各自的增益。
- 其他决策模型的评测或个别用户的试卷成绩都不是 WorkBuddy 云服务的同题基线，不能拿来替代本阶段测量。

## 本次不做

不更换用户当前官方 Jev 配置，不触碰 Key、账号档案、控制台 EXE，不调用付费模型做批量试验，不在没有前后对照数据时宣称准确率提高。
